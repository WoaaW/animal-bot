# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mudae-style Discord bot for animals. Users `/rescue` (alias `/rc`) to roll random animals and click a button to **rescue** them into their **sanctuary**; each guild has its own rescue pool. The "rescuing" framing is deliberate — we avoided "claim/harem" to keep the tone wholesome.

Stack: Python 3.10+, `discord.py` 2.x, SQLAlchemy 2.x async, SQLite (via `aiosqlite`), `python-dotenv`.

## Setup & run

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e .
cp .env.example .env          # then paste your bot token
python -m bot.seed            # populate the animal table (idempotent)
python -m bot                 # run the bot
```

Re-run `python -m bot.seed` after editing `bot/data/animals.json` — it skips animals that already exist by name.

## Architecture

- **Entry point**: `python -m bot` → `bot/__main__.py`. Initializes the DB schema, loads cogs, starts the bot, syncs slash commands globally on `on_ready`. Global sync can take up to an hour to propagate; use `bot.tree.sync(guild=discord.Object(id=...))` for instant per-guild sync during dev.
- **Async-only**: discord.py runs on asyncio, so the DB layer is async (`aiosqlite` + `async_sessionmaker`). Never use the sync SQLAlchemy API in handlers — it blocks the event loop. SQLAlchemy's async support also requires `greenlet`, which is why the dep is pinned as `SQLAlchemy[asyncio]` (the extra pulls greenlet in).
- **Defer slash commands that touch the DB**: Discord rejects interactions if not acknowledged within 3 seconds, and a cold-start aiosqlite connection can blow that. Pattern: validate cheap preconditions → `await ctx.defer()` → run DB work → `await ctx.send(...)`. Button callbacks get their own fresh 3s window and don't need this.
- **Hybrid commands**: every command is a `commands.hybrid_command` taking a `commands.Context`, so it works both as `/rescue` and as `!rescue` (prefix from `COMMAND_PREFIX`, default `!`). Use `ctx.send`/`ctx.defer`/`ctx.author`, not `interaction.*`. With a prefix command, `ephemeral=True` is ignored and `defer()` just shows typing. A multi-word text argument must be keyword-only (`*, animal: str`) to take the rest of the message. Prefix commands need the privileged `message_content` intent, enabled both in `__main__.py` and in the Developer Portal. Hybrid `aliases=` only apply to the prefix side, so a slash alias (`/rc`) is a separate `app_commands.command` that builds a `Context.from_interaction` and calls the hybrid command's callback. `help_command=None` because `/help` replaces discord.py's built-in help. A command with subcommands is a `hybrid_group` with `fallback=` (a slash group can't run by itself, so `/reserve view` is what `!reserve` does); `/help` lists each subcommand.
- **Cogs**: Commands live in `bot/cogs/*.py`. Each cog defines a `setup(bot)` coroutine and is loaded by name in `__main__.py`. To add a cog, create the file and add `await bot.load_extension("bot.cogs.<name>")`. `/help` (`bot/cogs/help.py`) lists commands straight from `bot.tree`, so a new command shows up automatically — give it a meaningful `description`.
- **Data model** (`bot/models.py`):
  - `Animal` — global pool of rollable animals. `name` is the French common name of a *specific* species (e.g. "Dauphin rose de l'Amazone", not "Dauphin"; no per-animal pet names), plus `scientific_name` (binomial), `rarity`, and fields the seed fetches: `description` (full lead section of the French Wikipedia article, plain text), `image_url`, `wiki_url`, `iucn_status` (Wikidata P141, e.g. `EN`), and `taxa` (scientific names of its families, orders and classes, `|Felidae|Carnivora|Mammalia|`, several per rank when Wikidata has competing classifications). `name` is the seed's identity key.
  - `PlayerState` — per `(guild_id, user_id)`: `points`, `peak_points` (raised in SQL by every points gain: `add_points`, `collect_reserve`), roll counter (`rolls_used` within `rolls_period`), `claims_anchor` (claim regen, see below), reserve income state (`reserve_anchor`, `reserve_remainder`), and shop upgrade levels `extra_rolls`, `luck_level`, `claim_slots`, `reserve_slots`, `appeal_level`. Upgrades are stored as levels over the defaults, so changing a default (`BASE_ROLLS`, `RARITY_ODDS`…) still reaches every player. Rows are created lazily. (An old unused `rarity_multipliers` column may linger in existing DBs.)
  - `Rescue` — one row per rescue, `(guild_id, user_id, animal_id)`. No unique key: the same animal can be rescued any number of times, by several players or by the same one (`/sanctuary` groups them as `×N`, one section per rarity (rarest first, underlined header via `paginate_sections`, which repeats a cut section's header as "(suite)" on the next page), best appeal first within it, with the first rescue date as a Discord timestamp `<t:…:d>` (rescued_at is naive UTC), listing each copy's appeal, 🔺 before the name if one is in the reserve). Each row has its own `appeal` (1-5 stars, rolled with the roll) and `in_reserve` flag. Existing DBs that still carry the old `(guild_id, animal_id)` unique constraint are rebuilt by `_drop_removed_unique_constraints` (`bot/db.py`).
- **Roll flow** (`bot/cogs/rolls.py`): load *all* animals (rescued ones stay rollable and rescuable) → `consume_roll` → `_weighted_pick`: pick a tier by `rarity_odds(luck_level)` (locked tiers and tiers with no animal are skipped), then an animal uniformly within it → `roll_appeal` (shown in an embed field with its reserve income, stored on the `Rescue` if rescued) → a "Collections" field lists the collections the animal counts for with the roller's progress (N/5, ✓ when complete) → if the roller already owns this animal, a "Déjà dans ton sanctuaire (×N)" field lists their copies' appeal, best first, capped at `MAX_COPIES_SHOWN` → `add_points` the animal's `RARITY_POINTS` to the roller, in the same transaction as the roll → post embed (first two sentences of the description + image, built by `animal_embed(full=False)`) with a `RescueView` (`ROLL_TIMEOUT_SECONDS`, 60 s): "Rescue" button (costs a claim; only the roller can click during the first `ROLL_PROTECTION_SECONDS` (30 s), others get an ephemeral "réservé" message with a `<t:…:R>` countdown, which the wish ping line shows too; then anyone) plus "En savoir plus", which sends the full description ephemerally. On success the button is relabeled and a public follow-up announces the rescue (mention without ping). One rescue per roll message, guarded by an in-memory `rescued` flag set before any `await` (reset if the clicker has no claim). On timeout the view edits the message to disable its buttons. `/info <animal>` (autocompleted, accent-insensitive) posts the full embed for any animal. `/animals [rarity] [group]` lists the whole pool (or one collection, autocompleted; on the prefix side `_parse_animals_filter` splits "peu commun félins" into rarity + group), rarest first, marking who rescued each animal in this guild (first `MAX_RESCUERS_SHOWN` names, then a count). Long lists (it, `/sanctuary`) go through `paginate` + `send_pages` (20 lines per page, ⏮️◀️▶️⏭️ buttons, only the invoker can flip): embed descriptions cap at 4096 chars, so never put an unbounded list in one embed. Embeds link the title to `wiki_url` and credit "Source : Wikipédia" (CC BY-SA attribution) — keep that when changing them.
- **Wikipedia data**: `seed.py` first collects every animal missing a field (neither set in `animals.json` nor stored), then fetches them all up front in batches. French Wikipedia action API, `WIKIPEDIA_BATCH` (20, the TextExtracts max for `exintro`) titles per request, with `prop=extracts|pageimages|info|pageprops`, following `continue` and the reported normalized/redirect renames. Then Wikidata SPARQL queries on the article's item (`wikibase_item`): `fetch_taxa` walks `wdt:P171*` up to ranks family/order/class (`TAXON_RANKS`, `TAXA_BATCH` 100 items per query, 60 s request timeout). The query must anchor the items with a triple (`?item wdt:P225 ?sci`) before the path, or Blazegraph walks P171* backwards from every family/order/class and hits Wikidata's 60 s timeout; going through the item rather than matching P225 means synonyms don't matter. Note Wikidata nests birds inside the class Reptilia, so never build a group on `Reptilia`. And one query per `WIKIDATA_BATCH` items for P141 (IUCN status), skipping deprecated statements and preferring preferred ones; Endangered appears as either Q96377276 or Q11394. Lookups use the sentence-cased `scientific_name`: binomials redirect to the species article ("Inia geoffrensis" → "Boto") and never hit disambiguation pages. French Wikipedia sometimes only knows an older synonym (e.g. `Monachus tropicalis`, `Macropus rufus`, `Manta birostris`), so use that one when a binomial isn't found. Batching matters: Wikipedia rate-limits hard (HTTP 429 with ~45 s `Retry-After`), so per-animal requests took over an hour for ~300 animals versus under a minute batched. `_get_json` still sleeps and retries honoring `Retry-After`. Fetched values persist, so re-seeding only fetches what's missing. To override a value, set that field explicitly in `animals.json` — JSON wins. To force a refresh, clear the column (or delete `bot.db`) and re-seed.

## Conventions

- **Player-facing text is French** (messages, embeds, buttons, command descriptions); code, comments and identifiers stay English. "roll" and "claim" are kept as game jargon, as French Mudae players say them. Rarity keys (`common`…) are identifiers: display them through `RARITY_LABEL` (`bot/cogs/rolls.py`). `/animals` takes its rarity via `app_commands.choices` (French names, key values) and also accepts a typed French label or key on the prefix side. Command names are still English (`/rescue`, `/shop`, `/reserve add`…).
- **Rarity = IUCN status**, via `IUCN_RARITY` in `bot/cogs/rolls.py`: LC→common, NT→uncommon, VU→rare, EN→epic, CR/EW→legendary, EX→mythic (hidden tier above legendary, reserved for extinct species, worth 500 points). The seed recomputes it every run, so a reassessment on Wikidata changes it once `iucn_status` is cleared and re-fetched. `RARITY_ODDS` are per-*tier* percentages (common 60 → mythic 0.1), independent of how many animals each tier holds. Animals with no usable status (DD, domestic species) must set `"rarity"` in `animals.json` — the seed skips new ones otherwise. An explicit `rarity` always overrides the IUCN mapping.
- Animal pool lives in `bot/data/animals.json`: `name` + `scientific_name` only; everything else is fetched. An explicit `rarity` must be a key of `RARITY_ODDS` — the seed refuses to run otherwise. Editing this file + re-running `bot.seed` is the way to add content; don't insert via ad-hoc scripts. Keep tiers balanced: odds are per tier, so a thin tier makes each of its animals over-frequent (aim for animals-per-tier roughly proportional to `RARITY_ODDS`). To find real species of a given IUCN status, query Wikidata SPARQL for `p:P141/ps:P141 <status item>` + `wdt:P105 wd:Q7432` + a frwiki sitelink, ordered by `wikibase:sitelinks`. Filter to animals by walking `wdt:P171` level by level up to Q729: `wdt:P171+` times out.
- Discord IDs are 64-bit — always use `BigInteger` for `guild_id` / `user_id` columns, not `Integer`.
- **Currency**: every roll grants the roller `RARITY_POINTS[rarity]` of the rolled animal (in `bot/economy.py`), stored in `PlayerState.points`, keyed by `(guild_id, user_id)`. Rescuing gives no points; it only adds the animal to the sanctuary. Use `add_points` (a SQLite upsert with an in-SQL increment), never read-modify-write. The currency's final name isn't decided yet: always display it through `CURRENCY_NAME`. `/balance` shows the balance. A shop is planned (e.g. buying extra rolls).
- **Roll limit**: `BASE_ROLLS` (10) + `extra_rolls` per window of `ROLL_RESET_SECONDS` (1 h), in `bot/economy.py`. Windows are fixed clock slots shared by everyone (`time // ROLL_RESET_SECONDS`), not per-player timers.
- **Claims**: rescuing costs one. They regenerate one per `CLAIM_REGEN_SECONDS` (60 s) per player, stockpiling up to `BASE_CLAIMS` (1) + `claim_slots`. Stored as a single `claims_anchor` timestamp: available = `min(cap, (now - anchor) // regen)`; spending sets `anchor = max(anchor, now - cap*regen) + regen`, which keeps partial progress. 
- **Luck**: `rarity_odds(level)` in `bot/cogs/rolls.py`. A tier is rollable once `level >= RARITY_UNLOCK_LEVEL[tier]` (everything from level 0, except mythic at 5), and each level multiplies a tier's weight by `1 + LUCK_STEP × rank` so rarer tiers grow faster. The shop shows the mythic tier as "???" until it's unlocked, including in the luck field's "Au niveau suivant" preview (luck and appeal both preview next level's odds).
- **Reserve** (`/reserve view|add|remove`, `bot/cogs/reserve.py`, logic in `bot/economy.py`): rescued animals put on show earn `reserve_income(rarity, appeal)` points per hour = `RESERVE_BASE_INCOME[rarity]` × the `APPEAL` multiplier (halves round up). Appeal base odds and multipliers are in `APPEAL` (★ 45 % ×1 … ★★★★★ 2 % ×5); the odds are per player via `appeal_odds(appeal_level)` (shop upgrade, each level multiplies a star count's weight by `1 + APPEAL_STEP × (stars - 1)`, like luck), using the *roller's* level whoever rescues; rarity still matters, so a legendary ★ out-earns a common ★★★★★. `BASE_RESERVE_SLOTS` (1) + `reserve_slots` places. Income is computed lazily, like claims: `collect_reserve` pays `rate × min(now - reserve_anchor, RESERVE_CAP_SECONDS)` (12 h), counted in point-seconds so the fraction of a point carries over in `reserve_remainder`, guarded by a conditional UPDATE on the anchor it read. It runs before every place/remove (so an animal never earns for time it wasn't there) and when opening `/reserve view`. `place_in_reserve` checks the slot count inside its UPDATE (with an aliased subquery, or SQLAlchemy correlates it away). Typed names pick the best copy to add / the weakest to remove; autocomplete sends `#<rescue id>`. `/admin reset` empties the reserve along with the upgrades. Rescues from before the reserve get a random appeal in `init_db` (`_roll_missing_appeal`, `appeal = 0` means not rolled).
- **Collections** (`bot/species_collections.py`, `/collections [groupe]` in `bot/cogs/species_collections.py`): rescue `COLLECTION_TARGET` (5) distinct species of a group (`COLLECTIONS`: label, taxa names matched against `Animal.taxa`, difficulty). Same target for every group; the reward follows the difficulty (`DIFFICULTY`: easy 3 % … extreme 30 %), tiers set from the expected hours of rolls to find 5 species of the group, so recompute them when the pool changes a lot. Bonuses add up and raise reserve income (`_reserve_rate` returns the rate with the bonus, rounded down). Nothing is stored: completion is computed from the species the player currently owns, so trading away the last copy of a species can undo an collection and its bonus. The rescue button collects the reserve before inserting (a new bonus mustn't apply to past time) and announces newly unlocked collections in its public message; duplicates can't unlock anything.
- **Milestones** (`bot/milestones.py`, `/milestones [groupe]` in `bot/cogs/milestones.py`): rescue *every* species of a big group (`MILESTONES`: mammals, birds, reptiles, amphibians, fish, invertebrates; every animal of the pool must fall in exactly one). No reserve income; they're meant to unlock a future prestige. Nothing is stored: completion is computed from the species owned and the current pool, so a trade or a new animal in the pool can undo one. Rescues and trades announce them.
- **Shop** (`/shop`, `bot/cogs/economy.py`): five permanent upgrades (rolls, luck, claim storage, reserve space, appeal; icons are plain colored shapes 🔷🟢🟨🔺🟣, a 5-button row is Discord's max) defined in `UPGRADES` (`bot/economy.py`) as `(level column, base price, growth, max level or None)`; price = `base × growth^level`. Caps (25 rolls/h, luck 10, 6 claims, 5 reserve places, appeal uncapped) are written as totals minus the default; `buy_upgrade` refuses past them and the shop disables maxed buttons. Each shop field starts with a progress bar `|***---|` 3/6 (one `*` per level inside a code span so Discord doesn't read the stars as markdown; uncapped upgrades show their level). Upgrades after luck (claims, reserve, appeal) stay hidden, field and button, once `peak_points` (highest balance ever reached) covers their first level, or they own one (`visible_upgrades`): unlocked for good, even after spending; `ShopView._sync_buttons` rebuilds the button row after each purchase. `buy_upgrade` takes the level the player *saw*, so a double click can't charge for a level they didn't see.
- **Atomic spends**: every spend (roll, claim, purchase) is one conditional `UPDATE … RETURNING` via `_update_player`, so concurrent clicks can't overspend. Never read-modify-write player state in Python.
- **Bonus rolls/claims** (`bonus_rolls`, `bonus_claims`): handed out by `/admin give`, spent only after the regular ones, no expiry, no cap. Use these rather than bumping upgrade levels, which would inflate shop prices.
- **Wishes** (`/wish list|add|remove`, `bot/cogs/wishes.py`): a `Wish` row per `(guild_id, user_id, animal_id)` (unique, inserted with `on_conflict_do_nothing`), up to `MAX_WISHES` (10) per player. When an animal is rolled, `/rescue` pings every *other* player who wished for it in the roll message's content (`allowed_mentions` restricted to them) and shows "Dans ta wishlist" to the roller. Wishes survive a rescue (a better appeal is still worth hunting). The roll's wisher query lives in `rolls.py`, since `wishes.py` imports from it.
- **Admin** (`bot/cogs/admin.py`): `/admin give <points|rolls|claims> <amount> [member]` and `/admin reset [member]`. A `cog_check` restricts it to the application owner (`bot.is_owner`); `default_permissions(administrator=True)` only hides it in Discord's menu. `hidden=True` keeps it out of `/help`.
- **Trades** (`/trade <member> [give_animal] [give_points] [want_animal] [want_points]`, `bot/cogs/trades.py`, logic in `execute_trade`, `bot/economy.py`): each side can hand over one rescue and/or points, or nothing at all, so gifts are allowed. Same guild only. Options come from a `FlagConverter` (`!trade @membre give_animal: Panda roux want_points: 50` on the prefix side). The offer pins exact rescue ids and lives only in its `TradeView` (`TRADE_TIMEOUT_SECONDS`, no table, a restart drops it); only the target accepts, either can refuse or cancel. A rescue in a reserve can't be traded until removed. On accept, one transaction: `collect_reserve` for both (the bonus may change), conditional `UPDATE`s on the rescues (`rescued_at` becomes the transfer date), all debits, then credits via `add_points`, which raises the receiver's `peak_points` on purpose. A failed trade is not committed; the offer stays open unless the animal changed owner.
- Per-player state (currency, rolls, shop purchases) goes on `PlayerState`, never on `Rescue`. Still no release.
- **Schema changes**: there's no Alembic. `init_db` creates new tables and `_add_missing_columns` (`bot/db.py`) adds new columns to existing tables, so a new NOT NULL column needs a `server_default`. Dropped unique constraints are handled by rebuilding the table (`_drop_removed_unique_constraints`); renames, type changes and column drops aren't.
